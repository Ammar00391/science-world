## ما ورثه V23 من V22

- كان إصدار التطبيق في V22 هو `2.2.0+22` ورفع Android `targetSdk` إلى API 36.

### حالة البناء والإصدار

GitHub Actions مخصص للتحقق والتحليل والاختبارات، ولا ينشئ APK. إعداد Codemagic مخصص لبناء APK وAAB من نوع Release والتحقق من توقيعهما باستخدام هوية الرفع المحفوظة في إعدادات Codemagic. Gradle Wrapper 8.14 موجود ويعمل، لكن لم يُنتج APK أو AAB في بيئة العمل الحالية لعدم توفر Flutter وDart، ولم تُشغّل اختبارات Flutter أو بناء Release. إعداد Codemagic موجود لكنه غير مُتحقق ببناء فعلي؛ لا تعتبر النسخة جاهزة للنشر قبل نجاح البناء والتحقق من التوقيع وتثبيت APK وتجربة المسارات الأساسية.

1. خذ نسخة احتياطية قبل أي ترحيل.
2. لمشروع جديد: شغّل `supabase/schema.sql` كاملًا مرة واحدة؛ يحتوي على مخطط البداية وحماية حصص A1.
3. لمشروع موجود على V23: لا تشغّل ملف bootstrap كاملًا. بعد التأكد من تطبيق ترحيلات الاشتراك السابقة، شغّل بالترتيب إذا لم تكن قد طُبقت سابقًا:
   - `supabase/migrations/20261107_v23_vip_plan_durations.sql`
   - `supabase/migrations/20261107_v24_a1_question_entitlements.sql`
4. طبّق `supabase/migrations/20261107_v25_question_quota_40_silver15.sql` ثم `supabase/migrations/20261113_v26_question_quotas_and_attempts.sql`؛ V26 يحل محل سياسة V25 ويضبط الحصص إلى 3/6/40.
5. لا تعِد تشغيل ترحيلات مطبقة سابقًا دون مراجعة؛ احتفظ بنسخة احتياطية وافحص نتيجة كل تشغيل.
6. تأكد من نجاح الدوال والصلاحيات دون أخطاء. لم تُشغّل هذه الترحيلات على Supabase الحي في إعداد A1 الحالي.

**لا تشغّل** `questions_schema.sql` أو `subscriptions_schema.sql` أو ملفات `functions/*.sql` أو migrations القديمة منفصلة؛ تم دمج ما يلزم منها في `supabase/schema.sql` لتجنب ترتيب خاطئ أو سياسات متعارضة. ملفات SQL القديمة أصبحت تنبيهات غير تنفيذية.

### ما الذي يجهزه السكربت؟
- profiles مع رقم طالب ثابت ينشأ من الخادم.
- books وحقول PDF التي يقرأها Flutter.
- questions وquestion_versions وquestion_tags.
- subscriptions وactivation_codes وactivation_logs وpayment_requests.
- exam_attempts الذي تقرؤه صفحة التقدم الحالية.
- سياسات RLS: المحتوى المجاني المنشور متاح للمستخدم المسجل، والمحتوى المدفوع يتطلب اشتراكًا فعالًا.
- RPC آمنة للأسئلة وتفعيل رموز الاشتراك.

السكربت لا يضيف محتوى تجريبيًا، ولا ينشئ رمز اشتراك خاصًا، ولا ينشئ مستخدم مدير.

## مفاتيح الاتصال

يستخدم Flutter رابط المشروع ومفتاح `Publishable` فقط عبر `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY`. لا تضع `Secret key` أو `service_role` في Dart أو APK أو `--dart-define`. مفتاح Publishable مصمم للعميل؛ حماية البيانات تعتمد على RLS وسياسات SQL.

## ما يحتاج إعدادًا منفصلًا بعد قاعدة البيانات

- Auth: تفعيل تأكيد البريد وضبط قالب الرسالة وSMTP قبل اختبار إرسال الرسائل.
- Auth: إضافة رابط إعادة التعيين `scienceworld://login-callback/` إلى قائمة Redirect URLs في Supabase؛ بعد فتح الرابط ينتقل التطبيق إلى شاشة تعيين كلمة مرور جديدة. اضبط Email OTP وSMTP أيضاً.
- Storage: إنشاء bucket خاص للكتب والمرفقات، ثم إعداد سياسات القراءة والتنزيل قبل رفع ملفات PDF.
- AI: نشر مجلد `supabase/functions/ai-chat` بعد ضبط `OPENAI_API_KEY` و`SUPABASE_PUBLISHABLE_KEY` ضمن Function Secrets. لا تضع هذه الأسرار داخل Flutter أو GitHub.
- الاشتراكات: توليد أكواد hash من جهة موثوقة فقط. لا تستخدم أي رمز قديم منشور في ملفات أو نسخ سابقة.

## Flutter وبناء Android

```bash
bash scripts/prepare_android_wrapper.sh
bash scripts/ensure_android_sdk.sh
flutter pub get
python3 scripts/validate_project.py
flutter analyze
flutter test --reporter expanded
bash scripts/prepare_release_signing.sh
flutter build apk --release \
  --dart-define=SUPABASE_URL="$SUPABASE_URL" \
  --dart-define=SUPABASE_PUBLISHABLE_KEY="$SUPABASE_PUBLISHABLE_KEY"
```

`python3 scripts/validate_project.py --production` يمنع إصدار المحتوى النهائي حاليًا لأن بنك الأسئلة المعتمد فارغ. CI الحالي يبني نسخة اختبار فقط.
